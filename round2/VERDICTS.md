## Operator notes (facts about the run; no verdict above was changed by them)

1. Notation: `depositMulti(32, 1, X, y, z)` lists the raw calldata words of an array call: offset 32,
   length 1, then the element words, so it is `depositMulti([X])` (y, z are unused padding words).
2. R09 `ledger` (triaged `rule_wrong`): the rule writer suspected "an artefact of how the sum is
   tracked", and that is correct. Sums run over the modelled accounts, and the deployer's 7,000e18
   tokens are held outside them, so the rule fails on any successful step. It is an engine
   limitation, not a rule-writer error. It is counted as neither. R09's verdict rests on `pair_product`.
3. Circuit vs EVM mismatches (R03, R05, R08, R12) were investigated before sealing. All of them are
   token slots whose deployed value is above the bit-level search width: maximum approvals, which
   this token decrements, and in R03 balances of 1e21 searched at 8 bits. The circuit keeps only
   the low bits of such a value. No BUGGY verdict depends on the circuit, because every attack above
   was replayed on the EVM. R12's NO BUG FOUND also rests on the exact search at full 256-bit size
   (1-3 transactions, every function modelled) and on 23 of 25 rules proven for all sizes. The
   bit-level part of R12's evidence is weaker than its row suggests.
4. R03's bit-level search ran at 8 bits: the width choice missed the 1e21 balances set up by its
   deployment. Its finding came from fuzzing on the EVM.
5. R10's INCOMPLETE comes from the loop over the array argument. The code only accepts length 2,
   but the engines do not derive that bound, so the loop counts as possibly longer than 64 steps.
